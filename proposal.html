The Room Is the Memory

Final project proposal · FILMEDIA 6/306: Media and Mediums · Manasvini

What it is

I'm making a program that has no storage. My laptop turns a short piece of code into beeps and plays them out loud. A microphone across the room records the beeps and turns them back into code. The computer runs that code, then beeps it out again, over and over.

The code is never saved anywhere. Between passes, the only copy is the sound travelling across the room. There is no error correction, so if someone talks, coughs, or the room echoes, some beeps get misheard and some letters in the code change. Those changes are permanent. After a few passes, "I am a program kept in the air" becomes "I am a program kkpt in the aiu." Eventually the code changes so much that it doesn't run anymore.

It's a game of telephone played by machines, where the room is the one garbling the message.

Why I'm making it

We usually think of software and files as weightless, as if they live "in the cloud" and nowhere in particular. But every file is physically stored in something: a chip, a disk, a cable, a server. When a file gets corrupted or a photo gets worse every time it's re-sent, that's the physical medium showing through. I wanted to make that visible by choosing the most obvious and fragile storage possible, which is sound in a room, so you can hear and watch the medium change what it carries.

This also has a real history. Some of the first computers, like EDSAC in 1949, stored their memory as pulses of sound travelling through tubes of mercury, and had to keep re-sending the pulses to remember anything. My project does the same thing with the air of a room.

How it connects to the course

  • McLuhan, "The Medium is the Message." McLuhan says the content of a medium is always another medium. Here the sound carries code, and the code carries a sentence. But what ends up deciding what the program says is the room, the medium itself, not the content I start with.
  • Kittler, "Gramophone." Kittler argues that the phonograph doesn't just record meaningful sound; it records everything, noise included. My microphone works the same way. It can't tell my signal apart from a cough, so the room's noise gets written directly into the program.
  • Kittler, "Code." Kittler treats code as a kind of writing with its own history. My project writes code on an unusual surface, air, and shows that what you write on changes what gets written.
  • Carey, "Technology and Ideology: The Case of the Telegraph." Carey says the telegraph separated communication from transportation: messages no longer had to physically travel. My project goes the other way. The message has to physically cross the room, and it gets damaged on the way.
  • Ihde, Technology and the Lifeworld. Ihde describes "background relations," technologies like lighting or heating that we stop noticing. The air and acoustics of a room are about as background as it gets. In this piece the room becomes the machine itself.
  • Manovich, "Principles of New Media." Manovich says new media objects are numerical and exist in many versions (variability). Every pass here produces a new version of the program, but the versions are chosen by the room, not by a user.

Form

A web page built with my own code in JavaScript. It turns text into tones, plays them, listens with a microphone, decodes what it heard, and runs it. The page shows the code changing on each pass, what the program outputs, and a live picture of the sound the microphone hears. It has two modes: a real room (a speaker and a microphone placed a few metres apart) and a simulated room, so anyone can try it without a second device.

The final project will be the working piece plus a short video of it running in a real room with people in it, since their voices are what rewrite the code.

Where it is now and what's next

The prototype works in the simulated room. In tests, the code survives unchanged at about 2 metres, drifts slowly at 3 metres, and breaks within a pass at 4 metres. Next I will:

  • test it in real rooms with a phone or USB microphone, and adjust distance and volume so the code changes slowly instead of breaking right away
  • decide what the starting program should say
  • film it running in a room with people
  • write the 1–2 page statement
